# Architecture

Written for whoever — person or coding agent — picks this up next.

## The shape of it

```
    two iPhones
         │
         │  HTTPS
         ▼
  a static host (GitHub Pages / Netlify / Vercel)
  serving young-lists/ verbatim: HTML, CSS, ES modules
         │
         │  supabase-js: PostgREST, Auth, Realtime websocket
         ▼
  one Supabase project
    ├── Auth          one account per person, email + password
    ├── PostgreSQL    the tables in supabase/migrations/
    ├── RLS           who may see and change which rows
    └── Realtime      changes streamed to the other phone
```

There is no server of ours anywhere. Nothing is built, bundled or transpiled.
The files in `young-lists/` are what the browser runs.

## Why it is built this way

**No framework.** The app is a few thousand lines of vanilla ES modules. That
is small enough that a framework would add more concepts than it removes, and
it means the repository can be edited and deployed by anyone without a
toolchain. If it ever grows past the point where that is comfortable, the data
layer (`js/data.js`) is already the only thing that talks to Supabase, so a
rewrite of the views would not touch the backend.

**No build step.** Deploying is copying a directory. That keeps the app
portable between hosts and keeps `git` the source of truth for exactly what is
running.

**supabase-js is vendored, not loaded from a CDN.** See
[`../young-lists/vendor/README.md`](../young-lists/vendor/README.md). It means
the service worker can cache it and the app shell opens with no network.

**Security lives in PostgreSQL.** The browser hides buttons for convenience
only. Every rule that matters is a Row Level Security policy — see
[`../SECURITY.md`](../SECURITY.md).

## Rules of the codebase

1. **Never build DOM from user data with `innerHTML`.** Use the helpers in
   `js/ui.js`; `el({text})` sets `textContent`. An item named
   `<img src=x onerror=alert(1)>` must always be four dozen literal characters.
2. **Never `prompt()`, `confirm()` or `alert()`.** `ui.js` has
   `promptDialog`, `confirmDialog`, `formDialog` and `actionSheet`.
3. **Register listeners once.** Wiring belongs in a module's `init*()`
   function, called once from `app.js`. Render functions replace content; they
   must not call `addEventListener` on an element they did not just create. For
   a shared element, assign `.onclick` rather than adding a listener.
4. **All Supabase access goes through `js/data.js`.** Views read `state` and
   call the exported mutations.
5. **Security is a database policy, not a hidden button.** Anything you rely on
   must be enforced in `supabase/migrations/0005_rls.sql`, with a test in
   `supabase/tests/rls_tests.sql`.
6. **Do not claim offline writes.** See below.

## State and synchronisation

`js/data.js` holds one `state` object and a tiny event bus. Views subscribe to
the slices they render (`lists`, `items`, `stores`, `trips`, `catalog`,
`members`).

One realtime channel is opened per household, carrying every table of interest,
and it is always torn down before a new one is opened — so channels cannot
accumulate as the user moves around or signs in and out.

When an event arrives, the affected slice is **re-fetched**, debounced by
150 ms, rather than patched from the event payload. At household scale a
refetch costs one small query and is always correct; hand-applied deltas drift
the first time an event is missed or arrives out of order.

## What "offline" means here

Honestly: **the app opens offline; it does not work offline.**

* The service worker caches the app shell, so tapping the home-screen icon with
  no signal gives you the interface rather than a browser error.
* Data is not cached. There is no write queue and no local database. Reading
  and writing both need connectivity.
* A banner says so, and failed writes produce an error the user can act on.

Adding real offline editing would mean an IndexedDB mirror plus conflict
resolution for two people editing the same list. That is a real project, not a
flag, and it is deliberately not pretended at here.

## The walking-order feature

The point of the app. A store owns `store_sections` rows, each with a stable
UUID and a numeric `sort_order`. A shopping list may reference a store; each
item may reference a section by id.

`groupItemsByRoute()` in `js/data.js` buckets items by section and orders the
buckets by `sort_order` for the list's current store. Items with no section — or
with a section belonging to a *different* store, which happens when a list is
reassigned — fall into one "Unsorted" group at the end. Nothing disappears.

Because items point at section **ids**, renaming a section is free. Deleting one
sets `store_section_id` to `NULL` on its items (`ON DELETE SET NULL`) instead of
deleting groceries, and the UI says how many items that will affect first.

## Data model

Full detail in [`../supabase/migrations/0002_tables.sql`](../supabase/migrations/0002_tables.sql),
which is commented. In brief:

```
households ──< household_members >── auth.users
     │
     ├──< stores ──< store_sections
     │                    ▲
     ├──< shopping_lists ─┼──< list_items          (list_id, household_id) FK
     │         │          │
     ├──< shopping_trips ─┘   └──< shopping_trip_items   (text snapshots)
     │
     └──< household_items      the household product catalog
```

Three deliberate choices:

* **Composite foreign keys.** `list_items` references
  `shopping_lists (id, household_id)`, so an item cannot claim a household
  different from its list's. The database enforces it, not the browser.
* **Snapshots in history.** `shopping_trips` and `shopping_trip_items` store the
  list, store and section as *text*, so a past trip stays readable after any of
  them is renamed or deleted.
* **A product catalog.** `household_items` is maintained automatically by
  `complete_shopping_trip()`. It already powers type-ahead, "often bought"
  quick picks and remembered quantities, and is where repeat-shopping features
  should build from.

## Testing

`tests/run_all.sh` runs everything.

* **Database** (`tests/run_db_tests.sh`) — spins up a throwaway PostgreSQL
  cluster, installs a small stand-in for the parts of Supabase the schema needs,
  applies the real migrations unmodified, and asserts behaviour as four
  different actors including an unrelated authenticated user and a signed-out
  one. This is where RLS is proven.
* **Application** (`tests/browser/run.mjs`) — the real `index.html` and modules
  in headless Chromium at an iPhone viewport. Only the network layer is faked.
* **Service worker** (`tests/sw/run.mjs`) — proves a redeployed file is picked
  up and that the shell still opens with the network off.

The split matters: the browser suite runs against an in-memory fake, so it
proves the *interface* behaves, not that the database does. Anything about
permissions, cascades or RPC semantics belongs in the SQL suite, against real
PostgreSQL.
